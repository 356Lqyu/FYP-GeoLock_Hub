## Recommendation

For a supervised FYP demonstration, keep the existing SQLite recovery architecture and use **two always-on paid Render services plus the planner disk**, after the remaining ingress, workload and recovery prerequisites pass. Start the budget discussion at **2 GiB / 1 CPU planner using the sealed compact artifact + 512 MiB validator + 1 GiB disk: $25 + $7 + $0.25 = $32.25/month**, plus the existing Supabase plan, any backup/egress/tax charges. This is a conservative demonstration budget candidate, not a capacity-qualified deployment approval. The minimum proven resource envelope must follow the actual measurements; do not promise 100 pickups just because the source permits that many. This choice requires the explicit compact/artifact configuration and provisioning; merely reducing the RAM of the default legacy configuration is not safe. A shorter separately approved demonstration period can reduce prorated compute costs, while journal retention/backup must remain deliberate.

Two 512 MiB paid services plus 1 GiB disk would cost **$14.25/month**, but should be considered only for an explicitly bounded demonstration workload if the measured memory/latency/headroom supports it and the graph is provisioned as the independently sealed artifact. Do not activate JSON graph compilation on a 512 MiB planner: that path was OOM-killed in prior testing. The original review Blueprint (8 GiB planner, 2 GiB validator, 10 GiB disk) would be about **$162.50/month** at current list prices; it is provisional and has never been deployed. Do not apply it blindly for a small FYP demonstration.

These figures use published web-service prices ($7/512 MiB, $25/2 GiB, $135/8 GiB) and disk pricing ($0.25/GiB-month). [Render compute pricing](https://render.com/pricing?trk=public_profile__reactions-text), [disk pricing](https://render.com/articles/how-much-does-cloud-application-hosting-cost-for-small-businesses).

If the department already offers a **maintained Linux VM with public HTTPS, persistent storage and an accountable operator**, that is the best zero-incremental-cost route to investigate first. It can retain SQLite and the two separate service identities without a database redesign. Availability and institutional permission are unknown; it is an alternative to request, not a provisioned resource. A free hosting requirement alone is not a reason to rush a new recovery protocol.

## 1. Render Free with an external PostgreSQL journal

### What existing Supabase state already provides

Local source defines immutable/request-bound snapshots, matrices, candidates, validation records and protected authorization receipts. `RoutingWorker` derives matrix/candidate request IDs from the original snapshot UUID and checks authorization receipts before replanning. Those are valuable reconciliation anchors; **they are not presently a drop-in replacement for every journal step**. This is a source review, not a current DEV catalog inspection.

The existing journal persists, among other things, the exact computed solver response/payload **before candidate submission**. Re-running CP-SAT after losing that payload is not a safe substitute: even with the same seed, wall-time fields or a different incumbent can change the submitted body and conflict with the existing immutable request. Nor can a final authorization receipt alone reconstruct every pre-authorization failure/intent/payload state. See `backend/routing/worker_service/orchestrator.py` and the local authority SQL's snapshot/matrix/candidate/validation definitions. No existing domain receipt table should be repurposed as a miscellaneous mutable worker log.

Do not place mutable leases/steps inside a sealed snapshot or candidate body: their digest/immutability contracts must remain intact. The hosted runtime would need an explicit external-journal adapter and durability/readiness checks in place of its mounted-disk requirement. Simply disabling the mount guard or calling ephemeral SQLite "persistent" is unsafe. None of those adapters/configuration changes were made.

A reuse-first design should examine which completed steps can be reconstructed from existing immutable records through new narrow owned lookups, then persist only the remaining recovery artifacts. That could reduce duplicate storage. It still needs a durable equivalent for the exact four-method computed response/payload, negative outcomes/intents and execution ownership; the current source does not establish those as completely recoverable already. Another option is a closer PostgreSQL implementation of `claim`, `get`, `save`, `operation_lock` and `read_saved_result`. That must preserve both snapshot-lock and authorization-operation-lock behavior, including their nested use in `plan_and_authorize`; replacing each with an unrelated expiring lock risks concurrency changes. Choosing the smallest safe schema/adapter requires a separate reviewed design and deployed-catalog preflight, not assumptions about existing table names.

### Required design before any implementation

1. **Bound ownership:** key jobs to the original snapshot/request/NGO and derive those relationships from protected existing records. Preserve the original request UUID across retries, process changes and redeploys. Do not create a new cutoff/snapshot automatically to conceal expiry.
2. **Durable immutable steps:** persist exact computed payloads and results with a step key, canonical content hash, format/software/graph/policy identities and equality-on-replay. Same key/same body returns the existing value; changed body is a conflict. A design could use two small private logical entities (job ownership/lease and append-only steps), or a justified equivalent. No new table/layout is approved by this document.
3. **Lease and fence:** use the database clock, atomic acquisition/renewal and a monotonically increasing generation/fencing token. A process whose lease expired must not publish a newer step or perform a protected stage after another process takes over. A lease in a separate table is insufficient unless stage-changing RPCs enforce the fence. Keep transactions short; do not hold a transaction while building a matrix or solving.
4. **Handle every commit gap:** write immutable intent/payload before a domain RPC; after an unknown response, query the protected receipt/object by the same deterministic request ID and expected digest, or replay the same idempotent body. Journal writes and existing RPC commits are separate transactions unless deliberately integrated. Do not claim exactly-once delivery; target safe replay with existing exactly-one domain effects where the protected database constraints establish them.
5. **Preserve trust separation:** graph, planner and validator keep separate restricted credentials and allowlists. Use narrow private RPCs with fixed search paths and reviewed owners/grants; no public table writes or service-role/postgres fallback. Lease fencing across role boundaries requires explicit per-role design. Do not let the planner invent an independent validator attestation.
6. **Keep NGO authority:** final route authorization still requires the original NGO's valid JWT and protected ownership/availability/custody checks. Persist no bearer/refresh tokens in journal bodies. After a crash/JWT expiry, the client can authenticate again and resume the same saved request; a background recovery worker must not impersonate the NGO.
7. **Retain evidence safely:** apply size bounds and retention policy without deleting unresolved intents/unknown commits or existing domain audit history. Journal payloads may contain private pickup/route data. Restrict table access and backups; expose only owner-scoped summaries/results through approved readers, preserving current location-eligibility/redaction rules when claims have been released or expired. Ownership alone must not resurrect historical private pickup locations. Measure DB size, WAL growth, CPU, connection/egress load and backup needs before selecting any free allowance.
8. **Controlled cutover:** version the backend adapter and private protocol, test fresh deployment and pending-request migration, preserve the old SQLite evidence during handoff, and define rollback without two active unsynchronized journals. Copying or importing live journals requires its own explicit approval; none was done here.

PostgreSQL row/transaction locks can support atomic claims, but session advisory locks are not a durable lease and are unsuitable as a cross-request ownership mechanism through transaction pooling. Supabase's role/RLS guidance also does not justify granting broad access to solve a storage problem. [PostgreSQL locks](https://www.postgresql.org/docs/current/explicit-locking.html), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

Required future disposable tests include stale-worker fencing, crash after each stage/commit, lost responses, concurrent claim/takeover, cross-NGO/role rejection, changed-body replay, stale snapshot/lease/custody, validator outage, authorization already committed, DB outage, pooler connection turnover, no token persistence and rollback. **No such redesigned journal has been implemented or validated.**

### Free-tier limits that the redesign would not remove

Render Free has no persistent disk, sleeps when idle and shares 750 instance-hours per workspace/month. Two continuously running services require 1440–1488 hours in a 30–31-day month. Intermittent FYP use can fit the hour budget, but cold startup and the graph artifact must be handled after every storage-losing restart. Existing tests already measured disabled 0.1-CPU startup longer than Flutter's five-second diagnostic deadline. A redesign would need explicit non-mutating warm-up/retry UX before creating a snapshot, and reliable validator readiness; keep-alive jobs are not a durability mechanism. [Render Free limits](https://render.com/docs/free).

The current runtime checks validator health once with a five-second deadline during prewarm and does not automatically retry a failed preparation. A sleeping Free validator can therefore leave a planner unready until operator recovery even if the validator subsequently wakes. External-journal storage alone would not fix this. A future Free design needs bounded dependency warm-up/retry and client readiness behavior without prematurely creating or replacing request identities. No such runtime or Flutter change was made here.

The compact artifact is disposable cache, unlike the durable journal. Free instances would need an approved external artifact source and independently pinned seal/current manifest checks. Never embed graph exports or privileged credentials in the image. Egress could be material: a roughly 75 MB artifact fetched on 30 cold starts is about 2.25 GB before other traffic (illustrative arithmetic, not measured account usage).

External durability is not a performance fix. The current workload evidence includes solver-budget failures at larger sizes and long 0.1-CPU matrix execution; a journal cannot make those meet the app's request/freshness budgets. Keep the existing freshness/lease/custody checks. A queue or asynchronous client flow would be another separately reviewed change, not permission to authorize a stale snapshot.

Existing Supabase cost/headroom is **unknown**: no DEV account/catalog was accessed. Incremental $0 is possible only if the existing plan has sufficient DB/CPU/connection/storage/egress headroom and an acceptable availability/backup policy. Published Free includes 500 MB database space and 5 GB egress, and pauses after a week of inactivity; Pro starts at $25/month and includes daily backups. Those limits are not evidence of the current project's entitlement, footprint or recovery readiness. A PostgreSQL commit surviving a planner restart is different from guaranteed database availability or a verified disaster restore. [Supabase pricing](https://supabase.com/pricing).

## 2. Render paid with the existing SQLite journal

Keep one planner instance with the persistent disk and one independently credentialed validator. Deploy the tested source/images only after reviewed configuration, exact trusted ingress, graph artifact/cache provisioning and a current recovery baseline. SQLite journaling, original UUIDs, saved steps and protected receipt lookup remain; no new database migration/grant is needed merely to host this design.

A disk survives ordinary restarts, but is not high availability. Disk-attached services have single-instance/deploy limitations. A consistent SQLite backup and off-service restore rehearsal are still necessary; a raw copy of a live WAL database is not sufficient. The prior synthetic volume SIGKILL/reopen test does not verify an actual Render disk or current DEV backup. Authorization records remain in Supabase and must be reconciled when restoring older local state. [Render disk behavior](https://render.com/docs/disks).

Paid services avoid Free idle sleep and remove the 750-hour limitation. Capacity, provider headers, actual DB latency and the hosted APK URL still need coordinated acceptance. If a larger case produces a solver timeout/no usable incumbent under the unchanged policy, buying RAM alone does not establish support for that case. For FYP, approve a clear bounded test workload rather than silently changing the optimizer objective or solver policy.

## 3. Practical free / low-cost alternatives

**University VM:** ask whether an existing maintained 4 GiB / 2 CPU Linux VM (planning budget, not a measured combined-host minimum), public HTTPS and persistent storage can be assigned. Keep two containers/service identities, private backend ports, explicit local proxy trust and backups. It avoids a new journal protocol and recurring external compute cost if provided. IT availability, operator support and network rules are not assumed to have passed.

**Oracle Always Free:** current official allowance for Always Free tenancies is 1500 A1 OCPU-hours and 9000 GB-hours/month, equivalent to 2 OCPUs/12 GB, subject to home-region capacity. It is ARM; the currently tested images are amd64, so the exact pinned stack must be built/tested for ARM before using A1. Idle instances can be reclaimed after the documented seven-day criteria. Persistent-disk backups and a restore runbook remain essential. Do not rely on older 4-OCPU/24-GB figures or assume this account has capacity. No signup, payment verification, VM or quota was attempted. [Oracle allowances and reclamation](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm).

**Railway Hobby:** a $5 monthly minimum counts toward usage. Current rates are $10/GB-RAM-month, $20/vCPU-month, $0.15/GB-volume-month and $0.05/GB egress. An illustrative combined average of 0.75 GB RAM, 0.025 vCPU, 1 GB volume and no billable egress totals $8.15/month; it is an assumption, not a forecast. Free offers $1/month of resources; a one-time trial is not permanent free hosting. Existing SQLite can use a volume after port/proxy/disk/recovery validation, but actual retained memory/CPU determines the bill. [Railway pricing](https://docs.railway.com/pricing).

**Koyeb Free:** one 512 MB / 0.1-vCPU instance per organization, no volume attachment, and automatic idle scale-to-zero. It does not provide two independent durable services for this design and therefore does not bypass the external-journal/cold-start/separate-validator work. [Koyeb Free instance limitations](https://www.koyeb.com/docs/reference/instances).

## Decision boundary

For the quickest safe managed demonstration, prefer paid Render + existing SQLite and an explicit small demonstration envelope; use a department VM first if its availability/operator/public HTTPS are confirmed and zero recurring cost is essential. Treat Render Free + PostgreSQL journal as a separate approved engineering project, not an environment-variable switch. No option is deployment-approved until the remaining workload, proxy, real role/network, backup/recovery, cost and hosted-APK acceptance gates are satisfied.
