## Implemented locally

`backend/routing/integration/worker.py` rebuilds Phase A inputs from DB-shaped source facts and C1 vehicle rows. It binds explicit policy, timestamps, owner, depot, source location, capacity, vehicle version, costs, service duration and donor/listing windows. Invalid or exhausted service windows are explicitly excluded. Zero fleet and missing roads fail closed. It runs the same four Phase B methods on one immutable input through C2. No capacity, vehicle, service policy or source ownership is invented.

`graph_worker.py` checks complete export counts/unique IDs, selects the active approved coverage, and reuses C2 directed shortest-distance paths with time on the **same** path. No reverse or straight-line arcs are invented. Export authenticity depends on the trusted RPC transport; a hash or JSON export alone is not authentication. Graph manifests explicitly name `PG_REAL_OUTPUT_0`: legacy REAL costs use PostgreSQL's current six-significant-digit output projection, followed by C2's maximum-six-decimal check. This is not lossless binary-float precision or a new measurement. All proposed functions pin UTC and extra_float_digits=0 so worker-session settings cannot change snapshot hashes or graph exports. Approval of this cost projection is an operational prerequisite; changing it requires a new reviewed graph/profile.

`validate_work_item` is a separate worker entry point: it reconstructs inputs from the trusted DB work item and invokes the existing independent validator without running a solver. It binds candidate, snapshot and matrix DB digests, Phase A input/matrix hashes, execution weights and validator build. PostgreSQL jsonb hashes and Python canonical JSON hashes are distinct; the code never equates them.

The configurable proposed secondary objective remains fixed vehicle cost plus distance cost, after minimizing unserved tasks. The distance-only method remains the third comparator. This preserves the documented difference from the thesis's distance-only secondary objective.

## Authority and lifecycle

1. Trusted graph worker installs an explicitly approved policy and freezes approved coverage. No policy, graph, source task or vehicle is seeded by the migration. Graph fingerprinting uses bounded 10,000-row keyset hash pages rather than one multi-million-row JSON aggregate.
2. NGO calls `begin_my_routing_snapshot(request,policy)`. Owner comes from `auth.uid()`. One MVCC SELECT captures raw task/claim/lease/listing/donation/hub facts, unheld available vehicle definitions and verified depot at a cutoff. Planning changes no source state.
3. Trusted planner reads `read_pending_routing_snapshot`; graph worker builds a directed matrix from the complete frozen export. Planner seals that immutable matrix to the snapshot and reads the sealed bundle. Async solving holds no lifecycle row locks.
4. Planner evaluates all four methods, retaining comparison reports outside dispatch authority. Only the proposed feasible candidate is submitted. Separate validator reads the DB work item, rebuilds input, validates, and attests exact digests. Optimizer success is advisory.
5. NGO authorizes the attested candidate with an explicit future departure and request UUID. PostgreSQL locks and rechecks current owner, depot, versions, source fingerprints, claims/leases, locations, matrix arcs, capacity prefixes, service windows, timing, route duration, mandatory coverage and exact unserved complement. It creates native routes/stops and exclusive reservations, task CONFIRMED → PLANNED, route DRAFT → AUTHORISED, atomically. A candidate alone reserves nothing. Authorization is disabled until the C6 task guard is installed.
6. Existing `start_pickup` now requires the matching private permit. It rechecks route bindings, current source/vehicle/depot, stop order, current windows, remaining schedule and leases. A transaction-ID permit is consumed with the unchanged original pickup transitions. The task trigger rejects alternate DISPATCHED writes; no client-controlled bypass GUC exists.
7. Existing `complete_pickup` preserves original holder, lease, handover, donation, listing, hub and claim/lease effects. Collection, including the last pickup, retains route assignments and the vehicle hold. The owner must call `close_my_collected_route(route,true)` to confirm depot return. Closure verifies every task/claim/lease is collected/completed, clears only that route's assignments, marks it COMPLETED and releases private holds in the same transaction. It never toggles the vehicle's planning availability to true. The confirmation is an accountable NGO assertion, not GPS proof. Existing already-dispatched legacy tasks may finish through the captured completion path; legacy route cleanup is not silently assumed.
8. Only a managed, proven-unstarted route may cancel: no consumed permit, every task still PLANNED and its source fingerprint unchanged. The transaction archives its original stops immutably, removes those **unstarted planning** stops and assignments, returns tasks to CONFIRMED, closes the route CANCELLED and releases its hold. This archive move is an explicit approval-sensitive change because existing recovery treats any public historical stop as uncertainty. It is not deletion of executed pickup history. Started/partial/stale routes cannot use this cancellation path.

Donation lifecycles remain direct AVAILABLE → CLAIMED → PICKUP_IN_PROGRESS → COLLECTED, and hub SUBMITTED → HUB_ASSIGNED → AT_HUB → BATCHED → CLAIMED → PICKUP_IN_PROGRESS → COLLECTED. No donation state or ownership is created by routing.

## Security and concurrency review

- Ordinary NGOs receive only their protected APIs. No client NGO ID establishes identity. Planner cannot attest; validator cannot publish; graph worker cannot dispatch. NOLOGIN roles need separately approved backend login memberships and secure credential handling. No memberships, credentials or PostgREST authenticator grants are provisioned here. Standard service-role access alone cannot mint private routing permits.
- Worker functions verify the actual database session/role membership, not a caller-supplied JWT role string. This requires dedicated database worker authentication; an ordinary Supabase authenticated or service-role JWT will not work. Installer must be postgres; existing worker-role names cause an abort rather than unreviewed reuse. SECURITY DEFINER functions use qualified references and hardened search paths. Private tables are not directly exposed through APIs.
- Current route RPCs require READ COMMITTED. Lock order is owner profile → per-NGO advisory lock → sorted claims → leases → listings → their existing donation/batch/inventory locks → hubs → vehicles → routes → tasks. The legacy helper's existing donor/hub lock order is reused. C1 fleet guards still serialize vehicle edits on the same vehicle rows. Source state is rechecked after locks.
- Request UUID/payload digests and an owner advisory lock serialize publication retries. Changed payloads conflict; identical publication returns its recorded result, including after route closure. Candidate/snapshot/graph/matrix writes are similarly idempotent. Start is a one-use transition: retries after success fail closed, rather than inventing another permit. Completion retains existing retry behavior; cancel and explicit close are terminal-state idempotent by route ID.
- Partial unique indexes allow one outstanding booking per task and vehicle. This intentionally excludes future time-slot scheduling. A frozen plan becomes stale when authoritative source/vehicle/depot facts differ. Remaining timing and leases are checked at each stop; lateness does not fabricate collection. Last collection alone never releases a vehicle still away from the depot.
- Existing recovery may mark uncertain claims/leases RECONCILIATION_REQUIRED and tasks STALE. The new task guard permits that exact existing branch, retains reservations, and denies dispatch. Started/expired/reconciliation cases require a later protected resolution workflow; holds must not be removed automatically. Its full scheduler/trigger interaction still needs approved DEV tests.
- Cutover takes a task-table lock before capturing legacy in-flight IDs, draining old task writers. This avoids missing a pickup that commits during installation. No Flutter wrapper is treated as enforcement.
