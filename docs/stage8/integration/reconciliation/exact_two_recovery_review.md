## Scope and guarantees

The proposal permits only the two supplied expired claims and exact tasks. It requires direct donations so both final donation states can be AVAILABLE; it aborts on hub sources rather than changing hub lifecycle semantics. All guards precede the only mutating call, `n := public.recover_expired_claims(2)`. Uncaught exceptions abort the transaction, including recovery changes and audit inserts; COMMIT on an aborted transaction cannot commit partial recovery. There is no exception handler that suppresses errors, persistent wrapper function, direct record edit or permission change.

The recovery function is rechecked against body MD5 `5ff6d8719db9681aae6f444b89dfbaee`, expected owner/security/settings/signature/ACL. Both custody helper body pins are checked. The scheduler must exist once by name and be disabled; all active recovery jobs are rejected. The global pickup authority trigger must not already exist. This is a pre-003 operation, not a generic recovery tool.

Queue protection rejects every unrelated ACTIVE claim with an ACTIVE lease, including future expiries. SHARE ROW EXCLUSIVE table locks block queue inserts/updates/deletes and related custody/routing/reconciliation writes until transaction end. Both intended claim rows are explicitly locked NOWAIT before the function's SKIP LOCKED selection: another session's row lock causes failure instead of substitution. All source, listing, ownership, expiry and routing checks are re-evaluated while locks are held. Listing expiry may advance with time; if recovery switches to reconciliation, postconditions raise and roll back instead of committing that outcome.

Required outcomes: exactly two recovered; same source/lease/task IDs; claim/lease RELEASED with safe-release reasons and closed timestamps; tasks STALE; listings AVAILABLE/version +1; direct donations AVAILABLE; no reconciliation cases for either listing. The historical claim's complete claim/lease/task JSON snapshots must match before/after. Its shared listing/donation are intentionally allowed to change with recovery of the newer claim. Existing audit records must remain identical. Exactly four new events are required: two safe-release LEASE_RECOVERY events and two DONATION_STATUS_CHANGED events emitted by the existing custody helper, matched to target claims/leases/source IDs. Each target must also be the latest claim on its listing, matching that helper's audit association rule. Unexpected trigger-generated audit events cause rollback and review, not bypass.

## Locks, concurrency and limitations

The existing recovery lock order is claim → lease → listing → task → source donations/batch/inventory. This supervised wrapper first acquires table locks in that order, then reconciliation and routing relations, audit/config and scheduler metadata. It acquires both target claim rows in expiry/UUID order, then leases, historical rows, and source rows. This expands the original order to protect the full batch; it is deliberately maintenance-only. It is not a general online concurrent recovery protocol.

NOWAIT table/row locks fail immediately on conflicts. lock_timeout=5s bounds other waits; statement_timeout=30s bounds the DO statement; idle_in_transaction_session_timeout=60s limits abandoned sessions. These settings are local to the transaction. A timeout, deadlock or lock conflict aborts; never retry automatically or remove guards. Existing transactions can already hold row locks despite table locks being obtainable, hence explicit row checks and bounded waits remain necessary. The locks affect unrelated writers in the named tables: keep the interval short and schedule it.

SQL cannot prove Supabase project identity from database name. Verify DEV `rcgyuwiidqvrgbxswhqj` in the dashboard manually. Stop all application/API claim, pickup, planning, reconciliation and manual recovery writers; leave workers and scheduler disabled; allow no concurrent deployments, role changes or function replacement. In particular, table locks do not lock pg_proc against function replacement: fingerprint checks are observations, so the no-DDL maintenance condition is essential. Existing triggers and external side effects are not sandboxed by this wrapper; reviewed DEV trigger/security evidence must remain current.

The full audit-payload snapshot was unnecessary and could make nested JSON comparisons quadratic. The revised proposal streams an event-ID-ordered SHA-256 chain plus row count before/after, preserving a global check against altered/deleted historical audit records. Only the four current-transaction event payloads are materialized, after a count guard; PostgreSQL xmin identifies inserts/updates from this transaction, and updated old rows also fail the preserved-history check. Casting xid8 to xid matches xmin's type, including transaction-ID wrap. This retains an O(N) global scan and normal planner/sort costs, but avoids retaining all payloads or repeatedly comparing them. A target-only snapshot would miss unrelated audit tampering, so it was not substituted. The 30-second statement limit remains; very large DEV audit history may still require a separately reviewed approach.
