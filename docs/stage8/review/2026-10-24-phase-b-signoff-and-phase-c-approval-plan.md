### Why CP-SAT, and what differs from RoutingModel

CP-SAT expresses optional-node vehicle circuits, hard mandatory pickups, exact integer constraints and a two-pass lexicographic objective directly. Its OPTIMAL/FEASIBLE/INFEASIBLE/UNKNOWN statuses and objective bounds support precise reporting of proof versus incumbent quality. This is a defensible implementation choice for this bounded offline model, not a measured finding that CP-SAT is universally superior or faster.

OR-Tools RoutingModel is also suitable for vehicle routing with capacities and time dimensions. It offers specialized routing search; the thesis's PATH_CHEAPEST_ARC and GUIDED_LOCAL_SEARCH settings refer to that engine. **The current implementation does not execute those settings.** Their presence in preserved Phase A inputs must not be presented as applied configuration. Official references: [CP-SAT model and status semantics](https://developers.google.com/optimization/cp/cp_solver/) and [OR-Tools vehicle routing](https://developers.google.com/optimization/routing/vrp).

The implemented profile is OR-Tools 9.15.6755 CP-SAT, one worker, input seed, deterministic budget 0.25 per pass and half the input wall limit per pass (15 seconds each for a 30-second scenario). The pinned Python environment is 3.12.14. Time uses microseconds, weight millionths of kg, distance millionths of km and cost micro-units. Unsupported precision/ranges are rejected. Reproducibility means equal non-timing results in the tested pinned environment; wall-time-limited searches need not select the same incumbent across machines. Tied tours are not guaranteed to be mathematically lexicographically smallest.

Distance-only minimizes distance after coverage. Proposed minimizes `fixed_cost_weight * sum(used vehicle fixed cost) + distance_cost_weight * sum(vehicle distance * its per-km rate)` after coverage. Both weights default to one. This deliberately differs from the thesis's distance-only secondary objective. Costs in synthetic fixtures are synthetic units, not established NGO operating prices. The implementation optimizes already-authorized direct and hub-batch tasks; it does not create aggregation, transfer claims or choose hub membership.

### Actual security boundary

The inspected fleet/task/route/assignment tables have RLS enabled, no policies, and broad SELECT/INSERT/UPDATE/DELETE ACLs for anon/authenticated/service_role. **No-policy RLS denies ordinary anon/authenticated rows; broad ACLs alone do not mean these clients can currently write them.** RLS is not forced, and postgres/service_role bypass it. Protected functions owned by postgres operate through that trusted boundary. Existing `start_pickup` and assignment RPCs have EXECUTE for anon/authenticated/service_role; the holder checks prevent anonymous ownership success. No claim is made that anonymous users can collect donations.

Public-schema default privileges grant broad table and function access for objects created by the inspected owner roles. New routing objects therefore require explicit ACL/RLS hardening in the same transaction or a private schema with controlled defaults. Adding permissive policies without narrowing grants can expose writes. No custom task/route/assignment trigger currently supplies the missing dispatch gate. API-exposed schema configuration, external worker deployment, storage policy and credential handling are NOT VERIFIED by this catalog review.

## 4. Existing start_pickup bypass: required protected-RPC design

**The gate must be inside the existing protected `start_pickup(uuid)` transaction.** A Flutter condition or a new wrapper leaves its direct-call bypass open. The proposal preserves its signature and current claim/lease/listing/source checks and donation transitions; it adds an authorization precondition, with user approval required before implementation.

1. A trusted planner freezes authoritative inputs; a separately trusted validator checks the exact returned plan; a protected acceptance operation binds NGO, real vehicle, snapshot, matrix, validator/version and immutable plan digest. Candidate plans do not acquire claims or active route assignments.
2. Protected authorization issues one route authorization with individual task/claim items. Parent activation is single-use; each item is single-use for that claim. Consuming the parent at the first stop must not invalidate remaining authorized stops. Route activation alone must not mark all future donations PICKUP_IN_PROGRESS.
3. `start_pickup(p_claim_id)` locates the caller's matching authorization item. Under coordinated locks it rechecks owner, valid lease, task/listing/source state, validation/digests, vehicle availability/version, matrix/graph policy, authorization deadlines and execution time feasibility. Consume the item atomically with task DISPATCHED, donation CLAIMED → PICKUP_IN_PROGRESS and success audit. Failure rolls back consumption and lifecycle changes.
4. Add a database task-transition guard requiring a trusted authorization-consumption record bound to this transaction, actor and claim for normal transitions to DISPATCHED; narrow write privileges on permits/tasks. A caller-set session variable, text validation reference or client Boolean is insufficient. A database owner capable of changing functions is outside this enforcement boundary; privileged service access must be minimized and audited.
5. Replay uses a stable operation/item identity and returns the recorded outcome without a second transition. Failures return actionable authorization-required/stale errors without releasing or transferring claims. Rejected-action audit cannot depend on an insert rolled back by the same raised exception; use approved durable ingress/security logging if required.

Compatibility must be designed explicitly:

- An individual direct or hub pickup can obtain a validated **single-stop depot-return plan** for an actual owned vehicle through the same gate; existing callers can keep the claim-only RPC signature. A background service can prepare the permit before the existing pickup action.
- DEV currently has zero vehicles. A strict gate cannot preserve immediate pickup for an NGO with no real vehicle, usable matrix and valid authorization. Keep enforcement disabled until onboarding and permit preparation are ready; define any genuine non-vehicle/manual exception as a separately approved database policy, never an automatic fallback when planning fails.
- Already DISPATCHED pickups must remain completable through the existing protected completion/lease workflow. They do not need a second start. Pending claims require new valid authorization. Do not weaken expiry/recovery safeguards for compatibility.
- Frozen tasks may be CONFIRMED while protected publication legitimately makes them PLANNED. Record that exact authorized delta and current task token separately; do not mutate the sealed snapshot or blindly require its old status/version. Replanning must supersede old assignments through guarded operations without moving claim ownership.
- Phase A v1 starts at the snapshot cutoff. At a later real departure, obtain a fresh snapshot/replan or independently validate an explicitly bound execution instance against absolute windows, service/return times and DB time. Simply translating an old schedule is unsafe. Route activation expiry and remaining-stop deadlines are distinct; recheck each stop's current lease.
- Respect existing claim/lease/listing/task/batch/donation locking and derive one tested global order with route/vehicle/permit locks. The current assignment path locks route first; an informal lock sketch is not proof of deadlock safety. Concurrent recovery, cancellation, fleet edits and authorization need race tests before cutover.

## 6. Donation lifecycle preservation and review boundary

